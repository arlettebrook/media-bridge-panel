# ADR-0040 HLS 清单由面板中继一次：把相对地址补成绝对

- 状态：已采纳
- 相关：[0006](0006-redirect-for-playback.md)（本文是它的局部例外）、[0036](0036-image-endpoint-redirect.md)（同一取向的另一处）

## 背景

HLS 线路出现"同一个视频，一个客户端能播、另一个播不了"（VidHub 3.0.7 打 missav 的线路）。面板日志里唯一可复现的失败模式：

```
条目详情 → PlaybackInfo（1 个版本）
拉流 videos/{Id}/stream.hls → HTTP 302   目标 https://surrit.mrstcdn.store/{uuid}/playlist.m3u8
约 2 秒后 ffmpeg（Lavf/62.3.100）打面板：GET /api/emby/videos/{Id}/360p/video.m3u8 → 501
（480p / 720p / 1080p 各来一次）
客户端持续上报心跳，位置恒为 0.0s
```

既不是线路坏了，也不是线路要请求头（实测裸请求与带全套 `Referer`/`Origin`/`User-Agent`/`Accept` 取回的内容逐字节相同——源插件报的那组头是按页面链接拼的，不是实测结论）。真正的原因：**那份主清单里的地址是相对的**。

```
#EXT-X-STREAM-INF:BANDWIDTH=1126120,...,RESOLUTION=640x360,CLOSED-CAPTIONS=NONE
360p/video.m3u8
```

HLS 里相对地址按**客户端最初请求的那条 URL** 补全。客户端（ffmpeg 的 hls 解复用器）在 HTTP 层跟了 302，但解复用器手里的基准仍是 `/videos/{Id}/stream.hls` —— 于是三条相对地址被拼到**面板**身上，正是日志里那三条 501。直链（mkv/mp4）没有这个问题：URL 本身就是终点，一跳到底。

## 决定

**只把 HLS 清单这一跳改成"面板取回、改写、原样回"**，其余一切照旧 302：

- `finishStream` 判定地址是不是清单（路径以 `.m3u8` 结尾）：是 → 取回、把地址补成绝对、以 `application/vnd.apple.mpegurl` **200** 回；不是 → 与改前完全一致（302）。
- 改写的对象是**地址**：非 `#` 开头的整行，以及标签里 `URI="…"` 的值（`#EXT-X-KEY` / `#EXT-X-MAP` / `#EXT-X-MEDIA` / `#EXT-X-I-FRAME-STREAM-INF` / `#EXT-X-PART` …）。其它标签（含本站那个非标准的 `#EXT-X-TOKEN`）原样保留；认不出的地址原样留着，不猜、不把清单改坏。
- 基准取**跟随跳转之后的最终地址**（`res.url`），不是最初那个 `Location`。
- 三条硬约束：超时 15 秒；边读边数、超过**字节上限**立刻断开（**原定 256KB，后改 2MB** —— 见下）；取回必须真以 `#EXTM3U` 开头。任一条不满足 → 如实记一行并**退回 302**（`proxy` 档改为如实报错，见 0042/0044）。
- ⚠️ **字节上限 256KB 不够，已放宽到 2MB**（实测修正）：夸克**转码档**给的不是"几百字节的主清单"，而是**整片 VOD 清单**（每片几秒一条分片行）——一部剧的 4K 转码清单就有 **≈295KB**（实测 `content-length: 301863`，559 条分片）。撞上 256KB 会让这类线路**全部播不了**。真正的判据是开头的 `#EXTM3U`，字节上限只用来挡住"把媒体文件当清单读进内存"，2MB 远小于任何媒体分片、又覆盖得下整片清单。
- ⚠️ **超限必须 `break`，不能 `ctrl.abort()`**（实测踩过）：在读取循环里 `ctrl.abort()` 会抛 `AbortError`，被下面的 `catch` 当成"超时"，**把真实原因（字节超限）盖掉**，日志里只看到一句莫名其妙的"取清单超时（15 秒）"（而实际只过了几百毫秒）。现在用 `break`（迭代器自会 cancel body），超限如实报"响应超过 N 字节"。
- 分片与档位清单**仍全直连 CDN**：主清单里的地址补成绝对之后，由客户端自己按绝对地址去 CDN 取；那份档位清单里的相对地址（`video0.jpeg`）自然按 CDN 补全。实测档位清单 200、分片 200（1.08MB）。

## 理由

- **相对地址是协议层的事，不是站点的事**：放面板一处修，所有 HLS 源都受益。放源插件等于每个源各写一遍，还要各自新开一个**对客户端可连**的 HTTP 面（missav 那个源插件现在没有这种面）。
- **与客户端行为无关**：不依赖客户端读不读 `DirectStreamUrl`。
- **代价是一次几百字节的文本**，不是媒体流量（主清单实测 736 字节）。

## 备选

- **把真实地址填进 `DirectStreamUrl`**：用临时探针实测过（`catpaw_probe` 原样回来、query 键序一字不差），VidHub 确实读这个字段 —— 那么客户端会以 CDN 地址为最初请求，基准自然正确。**没选**：地址得在 `PlaybackInfo` 阶段就解析好（本条目 5 个版本 = 5 次上游 `/play`，全 HLS 的源更多），地址有时效（进详情页到真正开播之间可能过期），且"拉流时现取、不缓存"的既有口径要跟着重定；面板也更不知道哪个版本会被播。
- **把 `.m3u8` 包成 `.strm`**：`.strm` 是**服务端**读的约定（Kodi 那种客户端兼库的另说）；Emby 生态里是服务端读完、把里面那行 URL 当 `Path` 交给客户端 —— 而实测客户端不读 `Path`（面板写的 `Path` 形状是 `/api/emby/Items/{Id}/Stream/{token}/…`，客户端打的是 `videos/{Id}/stream.hls`，两种形状对不上）。真按 strm 语义做，等于面板替客户端去取，那一跳一点没省。
- **改 302 的落点**：无效 —— 基准是客户端最初请求的那条 URL，中间跳几次都不改变它。

## 后果

- **ADR-0006 多一条例外**：面板在 HLS 清单这一跳会碰内容（几百字节）；媒体字节仍然全在源与客户端之间跑。
- **面板多一次上游 GET**（每次开播一次）。取不回来时如实记一行并退回 302，行为与改前一致。
- **认不出的相对地址不会被改**（非标准写法），那种线路仍会撞 501 —— 日志里写着"补成绝对 N 处"，N 明显偏小时可据此定位。
- 该线路若**确实要求请求头**：主清单这一跳由面板带上，但档位清单与分片是客户端直连，仍带不了 —— 那种线路最终要靠源插件给代理地址解决，与本条无关。
