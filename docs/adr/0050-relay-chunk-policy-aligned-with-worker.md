# ADR-0050 面板中继的取块策略对齐 media-bridge-relay

- 状态：已采纳
- 相关：[0045](0045-relay-chunked-concurrent.md)（本文细化它的取块失败与超时口径）、[0042](0042-auth-line-byte-relay.md)、[0044](0044-emby-stream-playvia-relay.md)

## 背景

面板中继（`relayChunked`）与外部字节代理 [media-bridge-relay](https://github.com/dlushu/media-bridge-relay)（Cloudflare Worker）是同一套骨架的两份实现：探针 → 有界切块 → `threads` 路在飞 → 按序吐。两者长期在**取块的超时与失败口径**上不一致：

- 面板只有一级超时：`fetch` 的 15s 计时器**同时罩住连接与读满**，超时即整发作废并退避重试 3 发。
- 面板没有头部块对冲，起播首字节完全押在头一两发上，被一过性拒连就整段等一个超时周期。
- 面板重试对**所有**错误一视同仁（连 404/403 都白试 3 发），间隔固定 300ms；Worker 只对 429/5xx 多试。

Worker 已经在真机上把这三处收敛出一套更抗抖动、起播更快的口径（`CHUNK_TIMEOUT_MS` / `HEAD_CHUNK_TIMEOUT_MS` / `HEAD_HEDGE`）。两份实现各调各的，等于同一件事有两套事实。

## 决定

把面板中继的取块策略**按 Worker 的口径对齐**，不引入 Worker 环境特有的机制（子请求预算、声明长度等于实际吐出）：

1. **两级超时（慢判死）**：`timeout`（15s）只管连接与响应头，头一到即撤；另设"读满"硬上限 —— 头部块 10s、普通块 30s。到点判**该块失败**并走重试，不再让按序吐块的那一步无限期挂在这一块上。
2. **头部块对冲**：前 4 块各并发 2 路取先成功者（落败那发的字节丢弃）。
3. **重试口径**：3 发、间隔 200/500ms；**只对 429/5xx 多试**，其余 4xx 再确认一发即走。
4. 取块失败改为**返回结果对象**（`{ buf }` / `{ error }`）而非抛错，由调用方按"这一块失败"处理。

## 理由

- 三处都指向同一件事：**让单块的坏运气不再变成整段流的坏运气**。起播 TTFB 与"最差一次吞吐"是实测里真正掉链子的地方，不是稳态带宽。
- 对外契约（`playVia` 落法、端点形状、响应头）一律不动 —— 这是搬运内部的策略，客户端无感。
- 与 Worker 共用同一组常量与结果形状，两份实现可以互相参照，改一处能推另一处。

## 备选

- **照搬 Worker 的"块失败写流尾文本 + 正常 close"**：面板提前写死了精确 `Content-Length`，往流尾塞诊断文本会让实际字节数与声明不符；收益（客户端多拿到几十字节诊断）抵不上这处不一致。**没选**，仍以如实收场结束这一跳。
- **照搬猫爪源引擎 legacy 的"块失败无限重试 + 磁盘分块缓存"**：无限重试会把单块故障放大成持续打上游；磁盘缓存在路由器 flash 上既费寿命又是双倍磁盘 IO。**没选**。
- **照搬 Worker 的 `MAX_SUBREQUESTS` 子请求预算与"声明长度 = 实际吐出"**：那是 Cloudflare 单请求额度与 1101 的产物，Node 侧没有对应约束。**没选**。
- **只调常量、不改结果形状**：改动更小，但"抛错掀翻整条流"与"按块失败处理"是两种语义，光调常量到不了位。**没选**。

## 后果

- 起播 TTFB 更稳（头部对冲 + 更短的头部块超时）；单块慢/被拒不再按最坏 15s×3 拖住整段。
- 头部 4 块各多发 1 路，多消耗 256KB 级的重复字节（仅头部块，代价可接受）。
- 普通块的"读满"上限是 30s，比原来的 15s 宽松：这是 Worker 的口径（15s 只管连接），慢块的重任交给"读满上限 + 重试"。若实测发现路由器上 30s 偏松，可单独收紧这一个常量。
- 队列内的并发上限 `RELAY_MAX_THREADS`（32）**不在本次范围内**，仍待复测后另定（见 0045 的并发风险）。
