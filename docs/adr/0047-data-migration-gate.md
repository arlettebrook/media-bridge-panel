# ADR-0047 数据迁移框架：版本门禁 + 冲突处置向导 + 提交点续跑

- 状态：已采纳（已实现；首个任务是 [0046](0046-plugin-multiple-types.md) 的 v2 迁移。
  **交互口径于 2026-10-04 修订**：不再"每次升级都要人点确认"，改为**预检无冲突就静默迁移、有冲突才铺向导**，
  且**服务端启动时就自动跑**（不必等有人打开面板）——见第 4 节）
- 相关：[0046](0046-plugin-multiple-types.md)

## 背景

面板此前没有数据版本概念，数据布局变更靠"代码读到老形状就顺手修补"。这种做法在小改动下够用，但 0046 的插件目录拍平是破坏性变更（要移动目录、重写 registry、处置同 id 多包冲突），偷偷修补有三个不可接受点：

1. 迁移做到一半时进程已开始读写新布局，无法保证一致性；
2. 用户不知道数据被动了，冲突包（三个同 id 的 missav）需要人决定，没有交互入口；
3. 以后每次破坏性变更都要重造一遍轮子。

因此定一套**通用迁移框架**：面板知道"数据当前是什么版本、刚从什么版本升级上来"，在业务运行之前把迁移一项一项跑完；**只有需要人决定的环节（预检冲突）才铺向导**。

## 决定

### 1. 数据版本标记

- 文件：`data/.data-version`，内容为单个整数。文件不存在视为 **v1**（0046 之前的全部存量安装）。
- 代码侧写死"当前数据版本" `CURRENT_DATA_VERSION`；全新安装直接写当前版本，**不跑任何迁移**。
- 标记文件随备份打包（备份只排除点开头的**目录**，不排文件）：还原旧备份后标记也被还原，重启自动重跑迁移，闭环成立。

### 2. 启动门禁：三态

进程启动最早期（任何业务启动之前）读标记并比对：

| 情况 | 行为 |
|---|---|
| 数据版本 = 代码版本 | 正常启动（现有启动序列不变） |
| 数据版本 < 代码版本 | **迁移模式**：不 boot 插件、不起 Emby 监听、不挂定时任务；HTTP 只保留静态壳与迁移接口，其余 `/api` 一律 503 `{code:'MIGRATION_REQUIRED'}`。**进程启动时预检无冲突就直接静默跑完再启业务**（不必等有人打开面板）；有冲突时才铺向导（浏览器打开任意页面 → 迁移页，此时系统还没运行，它是唯一页面，不是普通弹窗），只列要决定的那几项（见第 4 节） |
| 数据版本 > 代码版本 | 同样进不了业务；向导显示「数据来自更高版本（数据 vN / 本面板 vM）」，提供**强制启动**逃生门（见第 5 条） |

迁移模式期间 Emby 实例端口完全不监听（客户端此时连不上是如实状态）。

### 3. 迁移程序：一套独立机制，以后所有破坏性变更加任务文件

```
server/core/migrations/
  index.js                       版本比对、任务表、串行 runner、提交点、状态落盘
  tasks/0002-plugin-types.js     首个任务（0046）
  tasks/0003-....js              以后每个破坏性数据变更新增一个文件
```

任务形状：

```js
{
  version: 2,                    // 完成后数据版本升到 2
  title: '...',
  irreversible: true,
  precheck(),                    // 只读扫描 → { conflicts, warnings }，不碰数据
  steps: [ { name, run(payload) } ], // 细步骤，断点粒度尽量小
}
```

规则：

- 数据版本 N、代码 M → 按序执行 N+1 … M 的任务；**中间缺号直接拒启报错**，不允许跳版本。
- **提交点在任务整体完成时**：一个任务（含其全部步骤）成功后才把 `.data-version` 升到该版本。
- 每个步骤必须**幂等**：重跑先自查"是否已在位"（目录已在新位置、registry 已是新形状即视为完成）。
- 执行状态落盘 `data/migration-state.json`：每步 pending/running/done/failed + 错误 + 日志尾部。进程在迁移中重启，向导能恢复现场。
- 启动时把残留的 `running` 一律重置为 `pending`（进程被杀没机会写 failed），靠幂等兜住，不允许任务永远卡在进行中。

### 4. 交互口径：无冲突静默、有冲突才铺向导（2026-10-04 修订）

**判据 = 预检里有没有"要人决定的东西"**（v2 就是同 id 多包冲突，或预检本身报错）。没有就静默跑完，有才铺向导；向导**只显示要决定的那几项**，不预先铺一屏迁移步骤。

1. **无冲突：静默迁移（服务端 + 前端各一道）。** 进程启动时，若处于 `migrate` 相位且预检没有需要决定的项，**服务端直接跑迁移再启业务** —— 无人值守升级 / 全新安装不必等有人打开面板。前端另有一道兜底：问一次 `/api/migration/status`，确认无需决定项就自己 POST `/api/migration/run`，页面上只有一张"正在升级数据"的进度卡（无按钮、无勾选），跑完 reload 直接进面板（覆盖"服务端自动跑失败、进程仍在迁移模式"这类现场）。
2. **有冲突：向导只列冲突。** 每组给出名字、类型、版本、data 是否为空，勾选要**删除**的副本（默认全选删除，每组最多保留一份，保留的随拍平迁移），按钮「解决并迁移」。
3. 迁移步骤表在**开跑之后**才出现（轮询 `/api/migration/status` 显示逐项进度）；跑之前的向导不显示它。
4. 迁移整体不可逆，但**不再单独设"勾选知悉"**：既然无冲突时已经默认静默跑（口径见上），在有冲突的分支再要求一次勾选只是纯摩擦。保险靠备份入口：向导放一颗「下载完整备份」按钮（维护态白名单放行只读的 `/api/panel/backup`）；迁移任务另自行复制它要改的关键文件（v2 复制 `registry.json` → `registry.json.bak-pre-v2`）。**不做服务端整卷自动快照**：容器里数据卷之外未必有可靠落点，塞进数据卷等于自己备份自己。
5. 全部成功 → 写最终版本标记 → **进程内续启业务**（顺序调用现有 boot 函数，不依赖外部重启策略），前端 reload 进入正常面板。
6. **失败退回向导**：静默迁移失败不留白屏或死卡。服务端自动跑失败时只记日志、**退回迁移模式**（业务照旧 503、下次启动还会重试，步骤幂等）；前端接管时重新取一次 status，把失败现场（哪一步失败、错误原文）摆进向导，处理完再点一次（断点续跑）。
7. **断点续跑**：迁移未完成（任务失败 / 手动关停 / 容器重启 / 断电），版本标记没到最终值，下次启动仍进迁移流程；已 done 的步骤跳过，从失败或未完成的步骤继续。不做"失败整体撤回"，也不做迁移成功后的自动回滚。

### 5. 数据版本超前的强制启动

- 超前时向导提供两颗按钮：**强制启动** / 退出（去升级面板）。
- 强制启动只把 `.data-version` 改写成当前代码版本，**不做任何数据转换**；执行前需勾选知悉（旧代码不认识新数据，可能报错、漏字段或写坏数据，后果自负）。
- 在 `migration-state.json` 留痕 `{type:'override', from, to, at}`，可审计。

### 6. 不提供迁移后回滚

迁移成功并开始运行业务后，插件会持续向新布局写数据（实例清单、缓存、更新换包、新装插件），此时目录级回滚必然丢失这些写入，旧版本也不认识新字段。因此：

- 迁移**过程中**靠提交点 + 幂等步骤保证不卡死；
- 迁移**成功后**没有后悔药：要降级只能停面板、切回旧代码、用事先下载的备份还原（迁移后产生的数据不带回）—— 属用户自负的降级操作，不是产品功能。

## v2 任务（0046）的步骤定义

1. 预检：扫 registry 找同 id 多条记录，列入冲突（只读，不动数据）。
2. 按向导里用户的决定删除冲突旧包（目录 + registry 条目）。
3. 剩余每条：`plugins/<type>/<id>/` rename 为 `plugins/<id>/`（已在位视为完成）。
4. 重写 registry.json：删 `type`、加 `types`，一条一包。
5. 删除空的类型目录；写 `.data-version = 2`。

## 后果

- 以后破坏性数据变更一律注册迁移任务，自动获得门禁、冲突确认、预检冲突处理、断点续跑；禁止再写"启动时偷偷修补"。
- 升级后**开机即自动完成迁移**（无冲突时），业务随即运行 —— 无人值守升级 / 全新安装不再被 503 拦住，也不必等有人打开面板；只有存在要人处置的预检冲突（或迁移失败）时才会停下来要人介入。
- 备份排除缓存的正则随目录拍平改为 `^plugins/[^/]+/data/cache(/|$)`，避免拍平后把插件缓存打进备份。

## 备选（已否决）

- **无条件静默迁移**（有冲突也静默）：冲突包没人处置、半失败也没现场。否决。**无冲突时的静默**于 2026-10-04 改回采用（见第 4 节）：没有要决定的东西就不该拦人；门禁与断点续跑照旧，失败会退回向导。
- **失败整体回滚 + 迁移成功后保留一键回滚**：迁移成功后新数据持续写入，回滚必然丢数据且旧代码不认识新字段，承诺不了无损；过程一致性由提交点+幂等覆盖。否决。
- **版本标记写进 settings**：settings 可被整体导入导出，容易污染版本判定；独立文件语义单一。否决。
- **迁移完成后退出进程交给 docker restart policy 重启**：依赖部署方式；进程内续启不引入外部依赖，且"迁移"与"启动"仍是两个分明阶段。否决。
